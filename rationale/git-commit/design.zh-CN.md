# git-commit skill 解析

`git-commit` 是一个把提交动作工程化的安全工作流。它的核心设计思想是：**提交是一道必须经过预检、分组、扫描、验证和留痕的质量闸口。** 因此它采用 7 步串行流程，而不是直接 `git add` + `git commit`。

## 1. 定义

`git-commit` 是一个安全增强型提交 skill。它会在真正执行提交之前，先验证仓库状态、识别暂存范围、扫描敏感信息、运行与生态匹配的质量门禁、生成符合 Angular / Conventional Commits 约束的英文提交说明，并在提交后输出结构化报告。

## 2. 背景与问题

这个 skill 要解决的问题是：团队把提交当成了一个过于随意的动作。

在没有约束时，常见问题通常集中在 5 类：

| 问题 | 典型后果 |
|------|----------|
| 仓库状态异常时仍然提交 | 把冲突、rebase 中间态、detached HEAD 一起提交进去 |
| 暂存范围失控 | 把不相关改动、临时文件、子模块指针一起带进 commit |
| 敏感信息未被发现 | API Key、私钥、数据库 URI 进入版本库 |
| 提交前不做质量验证 | 测试、lint、vet 没跑过，坏变更进入主干 |
| message 看似规范但语义失真 | scope 瞎编、subject 过长、一个 commit 混多个意图 |

`git-commit` 的设计逻辑，就是把这些高频失败点前移成强制门禁，并且让每一道门禁都有明确的输入、判断条件和失败出口。

## 3. 与常见替代方案的对比

在进入设计细节之前，先从整体上看 `git-commit` 与其他常见做法的差异，可以帮助建立一个直观的参照系：

| 维度 | `git-commit` skill | 直接 `git add && git commit` | 只做 commitlint / hook |
|------|--------------------|------------------------------|-------------------------|
| 仓库状态预检 | 强 | 弱 | 弱 |
| 暂存范围治理 | 强 | 弱 | 弱 |
| 密钥扫描 | 强 | 依赖人工 | 中 |
| 多生态质量门禁 | 强 | 常常缺失 | 中 |
| message 规范 | 强 | 不稳定 | 强 |
| 处理混合提交 | 强 | 弱 | 弱 |
| 提交后回执 | 强 | 弱 | 弱 |

它并不是要替代 hook，而是把 hook 之前那一层"智能化、结构化、面向用户交互的提交决策"补齐。

## 4. 核心设计逻辑

### 4.1 7 步串行流程

它的主流程是：

```mermaid
flowchart LR
  A[Preflight] --> B[Staging]
  B --> C[Secret Gate]
  C --> D[Quality Gate]
  D --> E[Compose Message]
  E --> F[Commit]
  F --> G[Post-commit Report]
```

这个顺序不是随便排的，而是严格按"越便宜、越基础、越应该前置"的原则设计：

1. `Preflight` 先检查仓库是否处于可提交状态。
2. `Staging` 再确认"这次到底准备提交什么"。
3. `Secret Gate` 在代码质量检查之前先拦截高危内容。
4. `Quality Gate` 只对已经确定要提交的内容做验证。
5. `Compose Message` 放在最后生成，因为 message 必须建立在"已知提交范围、已知改动意图、已知检查结果"之上。
6. `Post-commit Report` 确保流程有始有终，避免提交完成后没有回执。

这套顺序解决了两个很实际的问题：

- 防止把时间浪费在错误对象上。比如仓库还在 rebase 中，就没必要先讨论 message。
- 防止后置修复。比如先提交、再发现密钥泄露，这时成本已经高很多。

### 4.2 把 Preflight 做成硬门禁

`git-commit` 在最开始就检查冲突、detached HEAD、rebase / merge / cherry-pick / revert 中间态。这背后的设计思想是：**很多提交事故不是代码内容错了，而是仓库上下文错了**。

这种检查的价值在于：

- 它们成本极低，只需几个确定性 Git 命令。
- 它们一旦失败，后续步骤全部失去意义。
- 它们能显著降低"把 Git 中间状态误当成正常工作树"的概率。

换句话说，Preflight 不是锦上添花，而是"提交资格验证"。

### 4.3 把 Staging 单独设计成一层

很多提交工具默认假设"用户已经正确暂存"。`git-commit` 没有接受这个假设，而是明确把暂存识别视为独立问题。

它在这里有 4 个重要设计：

| 设计 | 设计原因 |
|------|----------|
| `> 8` 个变更文件时强制列全量文件并请求确认 | 文件一多就容易忽略细节，误提的概率随之上升 |
| 按逻辑意图分组，而不是按文件列表机械提交 | 一个好的 commit 单位是"一个变更意图"，不是"一组文件" |
| 单文件存在多个意图时允许 `git add -p` | 防止"文件级提交粒度过粗" |
| 对未暂存改动先 `stash --keep-index` 再做质量门禁 | 确保质量门禁验证的是即将提交的内容，同时不丢用户本地工作 |

**关于"8 文件"阈值**：这个数字并非随意选取。认知科学对人类工作记忆容量的研究表明，人在同时处理的对象超过 7±2 个时，出错概率会显著上升（Miller's Law）。超过 8 个变更文件的暂存集，人工逐一核对意图的可靠性已经大幅下降。选择 8 而不是"看起来很多"作为阈值，是为了给行为定一个清晰的触发点，让这道确认变成一个**可预期的安全网**，而不是模型凭感觉决定要不要问。

这里最亮的点是 `stash --keep-index`。它体现的是很成熟的工程判断：**提交前的测试应该针对即将提交的内容，而不是还夹杂着未暂存改动的工作区状态**。

### 4.4 敏感信息扫描采用"正则 + 分层 Triage"

仅靠人工看 diff，很容易漏掉 token、私钥和连接串。仅靠宽泛正则，又会产生大量误报。`git-commit` 在这里的设计不是二选一，而是两者结合：

1. 先用文件名和内容正则尽量多地捕获可疑内容。
2. 再按白名单、测试数据文件、文档、注释四类规则逐层过滤。
3. 只有经过过滤仍然存活的命中，才真正阻断提交。

这套设计解决的是"安全性"和"可用性"的平衡：

- 只有扫描，没有 Triage，用户会被误报拖垮。
- 只有人工判断，没有扫描，真正高危内容容易漏掉。

而且它把过滤顺序固定为"first hit decides"，结果稳定，不会因模型对具体情况的临时判断而出现差异。

### 4.5 质量门禁按生态拆到 references

`git-commit` 没把 Go、Node、Python、Java、Rust 的质量检查全塞进主文件，而是把它们拆进独立的 `references/quality-gate-*.md`。

这是一个很关键的设计取舍，原因有三点：

| 取舍目标 | 这样设计的好处 |
|----------|----------------|
| 控制主 skill 体积 | 主文件保持聚焦，只讲通用提交流程 |
| 按需加载 | 当前仓库是什么生态，就只读对应 gate |
| 提高可维护性 | 各语言门禁可以独立迭代，不会牵动主流程 |

更重要的是，它并没有把"怎么判断该跑哪个 gate"交给模型自由发挥，而是给出确定性规则：按生态统计 staged 文件数量（包含删除——删掉一个文件同样改变了「什么还能编译通过」），并按数量从多到少逐个执行命中的门禁。这个设计重点不是"聪明"，而是"可复现"。

### 4.6 message 生成被严格约束

这个 skill 对提交说明的约束非常硬，尤其是两条：

- subject 总长度必须符合仓库自身的上限；仓库没有声明时，默认小于等于 `50` 字符。
- scope 只有在历史里已经形成规范时才允许使用，否则直接省略。

这两条设计分别解决两个常见问题：

| 约束 | 解决的问题 |
|------|------------|
| 默认 `<= 50` 字符 | 防止 subject 变成"摘要里再塞一篇小作文" |
| 禁止凭空发明 scope | 防止 message 看起来专业，实际上在制造错误分类 |

"不要发明 scope"这一点尤其重要。很多工具会鼓励模型总是补一个 scope，但 `git-commit` 明确要求先用历史 commit 频率做发现，再决定是否使用。这种设计本质上是在反对虚假的结构化输出。

2026-04 的修订又把这条规则补强了两处：

- **只在新仓库里做 bootstrap scope**：如果仓库里的 conventional commits 总数少于 10，则允许在剥离 `src`、`pkg`、`internal`、`service`、`services`、`module`、`package`、`component`、`testdata` 等泛化目录后，从 staged 文件的最深稳定共享目录推断 scope。这样修复了"新仓库永远建不出 scope"的问题，同时又不会在成熟仓库里随意发明新 scope。
- **把 50 字符限制变成可执行 guard**：skill 现在要求在 `git commit` 前先执行 shell 层的长度校验和结尾句号校验。这样 subject 上限不再只依赖模型自觉，而是有明确的命令级防线。

2026-09 的修订来自一次外部评审，评审复现了脚本中的四个缺陷。每项修复都由一个「在旧版本上必然失败」的测试固定下来：

- **删除也要进入生态检测**：原先的 `--diff-filter=d` 把删除排除在外，于是「删掉被其他模块 import 的 `helper.py`，同时改一个 JS 文件」只会选中 Node 门禁，而此时 Python 包已经无法导入。删除恰恰是最容易让构建失败的改动，必须选中对应门禁。
- **读取失败即阻断**：`git diff | awk` 返回的是 awk 的退出码，因此 git 读取失败时，密钥扫描和生态检测都会输出为空并返回 0——这与「没有密钥」「没有生态」完全无法区分。现在两者都逐条检查读取结果并返回 2，因为*读不到*不等于*没有*。
- **各种序列化格式下的键值密钥都能识别**：旧规则要求小写键名后面紧跟 `=`，所以 JSON 里的 `"password": "x"` 和属性文件里的 `PASSWORD =` 都识别不到；正因为识别不到，它们还会在邻近命中的上下文行里被原样打印出来。现在匹配对大小写不敏感，且 `:` 与 `=` 同等对待，上下文行按同一规则遮罩。剩余风险（没有键名的短字面量）写进了 SKILL.md，而不是用一句代码兑现不了的承诺盖过去。
- **超时会升级到 KILL**：GNU `timeout` 不带 `--kill-after` 时，即使命令忽略 TERM 继续运行，它也会返回 124——coreutils 手册里就有这个例子。现在执行器会先探测 `-k` 再传入，超时就意味着进程组真的结束了。这种情况下 GNU 返回 137，SKILL.md 已与 124 一并说明。

同一次修订把 scope 判定从文字规则移进了 `scripts/resolve-scope.sh`。这些规则本来就是纯机械的——计数、比阈值、剥离、匹配——但把它们留在文字里，golden 测试就只能在 Python 里再实现一遍，于是那些测试证明的始终只是「一份实现与另一份实现一致」。改为在真实仓库上驱动实际脚本之后，这层同义反复就消失了。这次迁移还让一条文字难以讲清的规则得以落地：只有在 staged 文件中**不存在第二个 canonical scope** 时才采用该 scope，因此同时改动 `auth/` 与 `billing/` 的提交会直接省略 scope，而不是被贴上出现次数更多的那一个。

2026-09 的第二轮评审指出，第一轮修的是「报告出来的那几处」，而不是背后的整类问题。又复现并确认了四个缺陷：

- **路径按 git 的显示形式读取**：`--name-only` 受 `core.quotePath` 影响，`源码/配置.py` 会变成 `"\346\272\220…"`。扩展名被解析成 `py"`，`*.pem` 不再匹配，一次全是中文文件名的暂存因此完全检测不到生态——门禁被静默跳过。三个脚本现在都用 `-z`（原始、NUL 分隔）读取，补丁流则加 `-c core.quotePath=false`，这样命中报告里的路径是 `git show` 真正能打开的那一个。绝不要把 git 为终端转义过的字符串交给匹配器。
- **只检查了 git 这一段**：第一轮检查了 git 的退出码，却没检查分类器，于是 `awk` 损坏时脚本仍然返回 0 且没有任何输出——这正是「干净」的形状。现在 `set -o pipefail` 加上对每条管道的状态检查，任何失败的阶段都会自己报出来。*判断不了*不等于*没发现*。
- **检测与脱敏被混为一谈**：同一个函数既决定「这行算不算命中」又决定「从哪里截断」，导致 20 字符以上的长串规则只能作为兜底：`SESSION=<40 字符> password = x` 会在 `password` 处截断，把会话令牌整个打印出来——而且是在命中行本身，不只是上下文。现在这是两个决定：长串规则永远不产生命中，但永远参与截断位置的取最早。
- **超时保护会静默退化**：不支持 `--kill-after` 的 `timeout` 只打印一条警告就照用，下面的 perl 后备根本走不到。报告一个工具无法兑现的超时，等于告诉调用方进程组已经结束，而实际上门禁可能还占着锁和端口。现在不合格的工具直接跳过、继续往下找；若这台机器上没有任何能强制终止的实现，则返回 2，而不是以弱于自己所声明的保证去运行。原先*要求*退化后继续运行的那个测试，预期已被修正。

两轮下来的共同规律是：fail-open 很少只是一行代码。它是某个阶段无法区分「没有」和「判断不了」，因此修复必须覆盖所有可能产生这种歧义的阶段，而不是被演示出来的那一个。

2026-09 的第三轮发现了一个由**第二轮引入**的缺陷。`set -o pipefail` 是为了让阶段失败可见而加的；上下文提取器在 `NR > n + 2` 处提前退出；写入端是一条管道。三个选择单独看都正确，合在一起却产生一个只在超过管道缓冲区后才出现的误阻断：读取端离开时写入端仍在写，收到 SIGPIPE、退出 141，于是一次**已经完成**的上下文截取被报成扫描故障。三行时干净，两万行时返回 2——所以套件里所有小体积 fixture 都漏掉了它，包括专门为 pipefail 那次修复写的那些。

修法不是放宽检查。上下文阶段现在改由进程替换喂入：既保留提前退出（上下文按命中逐个渲染，每次全量扫描会是 O(命中数 × 行数)），又在结构上把写入端从状态里排除，于是 `if !` 重新只衡量它自己声明的那件事——awk 是否失败。here-string 也能做到，但在 bash 5.1 之前可能落到临时文件，而这个脚本必须能在 TMPDIR 不可写的环境里运行。

有两点可以推广：

- **单点覆盖找不到交互缺陷**：这里每个单独选择都有测试，故障住在它们的组合里，而且由一个没有任何 fixture 变化过的属性决定——体积。套件现在在**同一个测试里**断言小文件与大文件结论一致，这样回归就无法藏在一个通过的小用例背后。
- **阶段失败检查必须可归属**：一个删掉上下文错误检查的变异原本存活了下来，因为用来测它的 shim 让所有 awk 都失败，于是更早的阶段自己提供了 exit 2。现在 shim 只让某一次调用失败，测试断言失败的阶段必须**自己**报出错误。

同一轮补的是验证缺口，而不是新规则。`scripts/run_portability_matrix.sh` 会为每个可用的 awk 各跑一遍套件，并把缺失的实现报成 UNVERIFIED；若一个都没跑到就返回非零——空矩阵不是绿矩阵。这一点立刻起了作用：十二个凭证模式靠正则区间限定长度（`AKIA[0-9A-Z]{16}`、20 字符以上的长串规则），而不支持区间的 awk 会把 `{16}` 当字面花括号，什么都匹配不到，却打印出一个自信的"干净"结论。`secret-scan.sh` 现在会探测这项能力——脚本用到的字面形式与运行时编译形式都探——探不到就拒绝运行，而不是静默降级。真实 `gitleaks` 的契约测试在该二进制存在时运行，不存在时以**可见的 skip** 报出，因为另一种做法是把只用 shim 得到的证明悄悄算成覆盖。

最后，一个全流程测试按 §1 到 §7 的顺序在同一个仓库上执行，并断言真的落下一个提交。它不能证明 Agent **决策**正确——回路里没有 Agent——但它抓到了任何单元测试都抓不到的东西：SKILL.md 自己的 §7 报告命令会把被删除的中文路径打印成 `"\346\272\220…"`，用户读不懂，`git add --` 也不接受。路径转义这一类问题在三个脚本里都修了，却漏掉了紧挨着它们的文档命令。

2026-09 的第四轮回应的是一直悬着的证据问题，而不是继续加规则；而证据立刻改变了设计。

用临时容器（主机上未安装任何东西）在五个环境里跑了实际脚本：

| 环境 | awk | 区间支持 | 强制终止 | 完整套件 |
|------|-----|----------|----------|----------|
| macOS 15.6 | BSD awk 20200816 | 有 | perl 看护 | 通过 |
| Debian 12 | mawk 1.3.4 20200120 | **无** | GNU `timeout -k` | 通过，36 项跳过 |
| Debian 12 + gawk | GNU Awk 5.2.1 | 有 | GNU `timeout -k` | 通过 |
| Ubuntu 24.04 | mawk 1.3.4 20240123 | 有 | GNU `timeout -k` | 通过 |
| Alpine 3.24 | BusyBox awk | 有 | BusyBox `timeout -k`，**无 perl** | 通过 |

由此得到三个单机测试无论如何也测不出来的发现：

- **Debian 12 的默认 awk 匹配不了这些模式**。`mawk 1.3.4 20200120` 不支持正则区间，于是 `AKIA[0-9A-Z]{16}` 及其余十一个模式什么都匹配不到。本轮加入的能力探测会在那里直接拒绝运行，而不是打印一个自信的"干净"结论。Ubuntu 24.04 的 `mawk 1.3.4 20240123`——同一个标称版本——却支持区间；这正说明按版本号判断是错的测法，按行为探测才是对的。
- **BusyBox 的 `timeout` 根本没有实现 124 约定**。它报告子进程的信号死亡：普通超时是 143，带 `-k` 是 137。上一轮写进文档的"124 或 137"在 Alpine 上就是错的。执行器现在把工具作为子进程运行而不是 `exec`，并把"到达或超过截止时间的信号死亡"归一化为 124，判据是已耗时——这是任何实现都无法各执一词的那一项证据。调用方从两个退出码变成一个，契约因为被改正而变得**更短**。
- **一个套件可能对自己的适用范围判断错误**。在无区间支持的 Debian 上，首次运行有 31 项失败。脚本的行为是对的，是测试假定了一个有能力的 awk。现在测试按能力设门，跳过时给出点名该 awk 和修复方式的理由，于是 Debian 上的使用者读到的是"awk 不受支持"，而不是"这个 skill 坏了"。装上 gawk 后门自动打开、172 项全跑——这证明它是能力门，而非一刀切禁用。

真实 `gitleaks` 也第一次被实际执行，并纠正了两件事。退出码设计由二进制自己的 `--help`（"default 1"）和行为（`--exit-code 10` 返回 10）确认无误——但 v8.18.4 根本没有 `git` 子命令，任何调用都返回 1；脚本本来就对此 fail-closed，现在还会在错误信息里说明原因。它同时证伪了本仓库自己的一个测试 fixture：gitleaks **在白名单里放过** `AKIAIOSFODNN7EXAMPLE`（AWS 文档示例密钥），对它报告"no leaks found"。建立在该 fixture 上的测试证明不了任何关于真实扫描器的事。

还剩两处验证缺口，现在用工具而不是断言来应对。`scripts/run_cross_env_probe.sh` 只需要 bash、git 和 awk，因此能在没有 python 的地方运行——而那正是绝大多数精简镜像的情况，也正是此前所有非 macOS 行缺失的原因。`scripts/eval/` 探的是任何确定性套件都触及不到的那一件事：当授权模糊、改动混杂、或工具报出异常结果时，遵循这份指令的 Agent 是否会选对**分支**。它的 README 明确写出：它评的是 plan 模式下的一个决策声明、结果不确定、按次报告而不做平均、缺失答案记为 INCOMPLETE 而不计入分数。

最后，指令本身被缩短了。`SKILL.md` 曾把每条契约背后的推理都写在正文里，而 Agent 每次调用都要重读，且与设计文档重复。可测证据移入了 `references/design-evidence.md`（仅在维护时加载），防止回涨的守卫用的是**字符**预算而不是行数——因为此前的膨胀是以长句形式塞进已有条目的，行数根本没动。

2026-09 第五轮修复了第四轮引入的两个回归，随后又在评测工具里发现第三个缺陷——它使第四轮自己记录的部分证据失效。

**失败的容器被汇总成通过**。矩阵用的是 `if docker run … | sed 's/^/    /'`，因此 `if` 判断的是 *sed*。容器以 42 退出时，输出却是「all 2 exercised implementation(s) pass」且退出码 0。完整模式里第二条管道 `pytest … | tail -3` 以同样方式掩盖了失败的套件。现在两处都先取状态再排版。故意**没有**对整个文件启用 `set -o pipefail`：该文件另有以 `head -1` 结尾的管道，其提前退出会被误报为失败——正是第三轮踩过的坑。

**取消信号不再到达门禁**。为统一超时退出码，`exec tool` 被换成了「后台启动工具再 wait」的包装层。原先是 `exec` 时，发给执行器的信号会直接打到工具上；包装层却什么都不转发。实测：向执行器发 SIGTERM 后它立刻返回 143，而门禁继续运行，两秒后写出了完成标记。现在包装层用 `set -m` 把工具放进自己的进程组，把 INT/TERM/HUP 转发给该**进程组**，等到组内清空，必要时升级为 KILL，然后才退出。

在写对之前我写错了两次断言，而错的那两次更有价值：

- 断言「取消后完全不产生副作用」是靠运气通过的。优雅终止先发 TERM，**正是为了**让门禁有机会收尾，而 shell 门禁会把当前那条语句执行完。那条断言实际上是在赌门禁跑到了哪一步。现在断言的是设计真正给出的保证：执行器退出前门禁已经结束，且之后不再出现新的副作用。
- 断言「进程组 kill 让取消更快」在正确代码上就失败了。当工具忽略 TERM、shell 门禁也扛过 TERM 时，组形式并不比 pid 形式快，两者都要等完宽限期。组形式真正买到的是**升级动作能触及整棵进程树**——只对 pid 升级会让这样的门禁永远活着。是变异测试逼出了这个区分：只回退转发的变异存活了下来，只有把升级也一并回退才会被抓到。

**评测的 skill 臂一直在没有 skill 的情况下运行**。`SKILL_DIR` 取自 `$0`，因此把运行器复制到别处以指向某个场景子集时，这个路径也跟着变了；`SKILL.md` 并不存在，标着 `skill` 的那一臂其实是第二个对照臂。四个已记录的格子是无效的，却被当成了成绩。值得说清它为何还能被发现：某次嵌套运行**明说**了文件不存在，并拒绝用它本可以找到的另一个 `SKILL.md` 顶替。要是它悄悄猜了，数字看起来会毫无问题。

运行器现在在没有 `SKILL.md` 时直接拒绝启动（退出 2），把 skill 路径、行数与哈希写进每份转录，使有效性可以逐格审计而不必从行文里推断，并支持 `EVAL_SKILL_DIR` / `EVAL_SCEN_DIR`，从此无需复制脚本。无效结果被删除而不是加注，评测目前的定论是「未测得决策收益」——两臂都通过的六个成对格子无法证明收益。场景 10 是已知唯一能区分两臂的用例，而且只在评分从「仅长度」收紧为「格式**且**长度」之后才成立：对照臂的 `Add reconciliation matcher stub` 在五十字符以内，却根本不是 Conventional Commits。

第六轮是一次纠正。第五轮把取消信号的缺陷报成了已修复。它没有修好，复测是对的：执行器仍然会在检查进程继续运行的情况下返回，而且有两种形态。

`SIGHUP` 在零秒内返回 129，门禁仍在运行；忽略 TERM 的门禁在执行器被取消后又活了十二秒，然后继续跑下去。原因是 perl 看护里第五轮从未看过的一行：子进程调用了 `setpgrp(0, 0)`。直接测得——perl `pgid 60922`，门禁 `pgid 60923`。第五轮新加的包装层是对*工具的*进程组发信号并升级的，因此那些信号全都落在只包含 perl 的组上。看护还完全没有设置 `$SIG{HUP}`，这就是 HUP 那一例不是"慢"而是"瞬间"的原因。

修复是删掉子进程的 `setpgrp`。隔离在上一层已经提供——`run_normalised` 用 `set -m` 把整次调用放进自己的进程组——因此 perl、门禁以及任何孙进程现在共享同一个可寻址的组，包装层的转发、等待组清空与 KILL 升级都能触及门禁。看护自己的信号处理因此变得多余并被删除：升级动作集中在一处，而不是在两处各实现一半。保留下来的是一道守卫：看护只对自己确实作为组长的组发信号，因为对并非自己领导的组发信号会波及调用方——那比正在修的问题更糟。超时时清理孙进程（`setpgrp` 原本存在的理由）已重新验证，依然成立。

更有用的教训是第五轮为什么会相信自己。它的测试驱动的是一个 `timeout` 替身，而那个替身把子进程留在了同一个进程组里——于是它从未复现出真正会出问题的拓扑。用理想化替身搭出来的测试，对着一个并不存在的系统确认了修复。现在的测试直接驱动真实看护，覆盖 SIGHUP 和忽略 TERM 的门禁，并另有一个测试陈述它们依赖的不变式：门禁所在的组必须可寻址，且既不能是包装层的组、也不能是调用方的组。把修复前的看护原样恢复，现在会被抓到。

有两个变异存活，两者都被记录而不是追着修。把看护旧的按 pid 转发的处理函数加回去不改变任何行为，因为共享进程组之后它们本就多余——这是等价变异，不是覆盖缺口。删掉取消消息背后的验证也会存活：那条消息原先无条件断言清理完成，现在会先复查进程组再声明，但"仍有进程残留"这一分支需要一个能在 SIGKILL 下存活的进程，测试无法构造。它只以结构方式固定，并如实标注为结构性。

### 4.6.1 Timeout Override 需要显式机制

原始的 120 秒超时规则是保守的，但对大型 Java 或多模块构建过于僵硬。现在 skill 把 timeout 定义成"有默认值 + 可覆盖链"的确定性配置：

- 默认值：无输出 120 秒。
- 覆盖来源：仓库 wrapper 配置（`COMMIT_TEST_TIMEOUT`）或环境变量（`QUALITY_GATE_TIMEOUT_SECONDS`、`SKILL_QUALITY_GATE_TIMEOUT_SECONDS`）。
- 操作规则：在长时间质量门禁开始前，先报告最终采用的 timeout。

这样既保留了"不能无限挂起"的安全属性，也去掉了"构建慢但健康，却被误判为失败"的假阳性问题。

### 4.7 提交后还要有报告

很多流程把 `git commit` 成功当成结束，`git-commit` 没这么做。它要求提交后输出短 hash、最终 subject、变更文件摘要和 gate 状态。

这个设计补上了三个价值：

- 让用户立刻确认"刚才到底提交了什么"。
- 让质量门禁结果有回执，而不是只在过程里一闪而过。
- 为后续 PR、审查、回溯提供统一输入。

所以它不是只关心"执行 commit"，而是关心"整个提交流程有没有完整收尾"。

### 4.8 hook 被拒绝后禁止使用 `--no-verify`

`git-commit` 在 Step 6 有一条明确规定：如果提交被 Git hook（commitlint、pre-commit、husky、lefthook 等）拒绝，必须读取报错、调整 message 以满足 hook，而不是用 `--no-verify` 绕过，除非用户明确要求。

这条规则背后的设计逻辑是：**hook 是团队合规层，不是个人工作流里可以自行绕过的噪音**。

- 项目里的 hook 通常是团队或组织明确写下来的规范——scope 白名单、ticket ID 格式要求、禁止 WIP 类型等。用 `--no-verify` 绕过，等于单方面声明自己的提交凌驾于团队规范之上。
- hook 拒绝本身就是信息：它告诉你 message 不符合规范，正确响应是修改 message，而不是消除这个反馈。
- 允许 AI 工具默认 `--no-verify` 会形成恶性循环：团队花精力配置了合规 hook，AI 工具把它们静默绕过了。

`git-commit` 的处理方式是：报告 hook 名称和具体报错，根据报错调整 message，并记录做了哪些调整。这样既解决了问题，又保留了 hook 完整的约束效力。唯一的例外是用户明确指示跳过——此时记录"quality gate: skipped by user"，把决策责任还给用户，而不是由工具替用户做这个决定。

## 5. 这个设计解决了哪些具体问题

从 `SKILL.md` 的规则和评估报告可以看出，它重点解决的是以下几类工程问题：

| 问题类型 | skill 中的对应设计 | 实际效果 |
|----------|-------------------|----------|
| Git 状态误判 | Preflight 硬门禁 | 在冲突、rebase、detached HEAD 等场景先停下 |
| 提交范围失控 | 分组暂存、`> 8` 文件阈值、`git add -p` | 减少混合提交和误提文件 |
| 敏感信息泄露 | 文件名扫描 + 内容扫描 + Triage | 提高发现率，同时降低误报 |
| 质量检查缺失 | 生态感知 quality gate | 提交前尽量保证最基本的 lint / test / vet 已执行 |
| message 失真 | 历史 scope 发现、长度限制、祈使语气 | 提高提交历史的一致性和可读性 |
| 绕过团队规范 | 拒绝默认 `--no-verify`，要求根据报错调整 | 保持 hook 合规层的完整约束力 |
| 流程不可审计 | Post-commit report | 给提交动作留下结构化回执 |

评估报告里的数据也支持这一点：`git-commit` 在 3 个测试场景、35 项断言中达到 `100%` 通过，而不用该 skill 的常规做法严格通过率只有 `23%`。2026-04 新增的回归层又补了 7 个 golden fixtures，覆盖 message 生成、scope bootstrap 和 timeout override 行为。这说明它的价值并不只是在"格式更好看"，而是在真实工作流里显著减少遗漏步骤。

## 6. 主要亮点

### 6.1 把"提交"从命令动作升级为质量闸口

这是整个 skill 最重要的亮点。它不再把 commit 看成一个机械命令，而是把它定义为代码进入历史之前的最后一道本地关卡。

### 6.2 强调确定性，而不是依赖模型临场发挥

这个 skill 里大量关键决策都不是"让模型猜"，而是"先跑命令，再按规则判断"，例如：

- 用 Git 命令识别仓库状态。
- 用 staged diff 而不是工作区猜测提交内容。
- 用扩展名和 marker file 选择 quality gate。
- 用历史 commit 频率决定 scope 能不能出现。

这说明它的设计目标不是让模型"显得聪明"，而是让流程"足够稳定"。

### 6.3 安全严格，同时不给日常开发增加不必要的负担

如果一个 skill 只有严格，没有降误报设计，用户最终会绕开它。`git-commit` 在这方面做得比较平衡：

- 敏感信息扫描提供 allowlist 和 Triage，而不是一刀切。
- 多生态门禁按需选择，不要求每个项目都跑一套大而全检查。
- 当用户明确要求跳过 gate 时，允许跳过，但必须记录状态。

这让它既能守住底线，又不至于变成"谁都不想用"的流程负担。

### 6.4 对边角情况做显式规定，而不是依赖默认行为

`git-commit` 对若干容易出事故的边角情况做了明确规定，例如：

- 空提交只能在用户明确要求时使用。
- submodule 指针变更必须再次确认。
- hook 拒绝后要根据报错调整，而不是直接 `--no-verify`。
- 超过 `120` 秒无输出的质量门禁要中断并反馈。

这类规则的价值在于，覆盖的不是一切顺利的正常路径，而是工程中最容易被忽略的异常情况。

## 7. 什么时候适合用，什么时候不该硬用

| 场景 | 是否适合 | 原因 |
|------|----------|------|
| 日常开发提交 | 适合 | 最能发挥预检、分组、质量门禁的价值 |
| 团队想统一 commit 质量 | 适合 | 能把隐性规范转成可执行流程 |
| 多语言仓库 | 适合 | 有生态感知 gate，不必手工切换 |
| 为了赶时间想一次塞很多不相关改动 | 不适合 | 它会主动阻止这种做法 |
| 明知要跳过所有检查只求快速留点 | 不适合 | 这和 skill 的设计目标相反 |

## 8. 结论

`git-commit` 的真正亮点，不是它会写 Conventional Commit，而是它把"提交前该做的判断"系统化了。它通过 7 步串行流程，把仓库状态检查、变更边界控制、敏感信息防护、生态质量门禁、消息规范化和结果回执串成一个完整闭环。

从设计上看，这个 skill 非常典型地体现了生产级 skill 的几个原则：**先建门禁、再生成内容；先收集依据、再组织语言；先管控风险、再追求流畅**。这也是它为什么能解决"提交动作太轻、风险太重"的根本问题。
