## 3) Executive Summary
Partial result: PostgreSQL's native logical replication (CREATE PUBLICATION / CREATE SUBSCRIPTION) ships schema and DDL changes to subscribers only if applied by hand; sequence state and large objects are excluded outright. Any pipeline built on top of the same logical-decoding mechanism (Debezium included) inherits the DDL blindness, because it is a property of the decoding layer, not of the consumer. PostgreSQL's native logical replication is a publish/subscribe protocol between PostgreSQL instances: the subscriber is itself a full PostgreSQL database that applies incoming changes. It has no built-in path to Kafka. Getting logically-decoded PostgreSQL changes into Kafka therefore always requires a separate consumer of the replication stream (a Kafka Connect source connector such as Debezium, a custom pg_recvlogical-based consumer, or a vendor CDC product) -- 'logical replication' by itself is not a second, competing way to reach Kafka, it is the underlying mechanism Debezium itself is built on. Debezium's PostgreSQL connector must be configured with a logical decoding output plug-in. decoderbufs is a Protobuf-based plug-in maintained by the Debezium community and requires separate installation; pgoutput is the standard PostgreSQL 10+ output plug-in maintained by the PostgreSQL community itself (the same plug-in used by native CREATE SUBSCRIPTION), so it needs no extra library.

## 5) Detailed Analysis
### How each option actually gets changes into Kafka
PostgreSQL's built-in logical replication (CREATE PUBLICATION / CREATE SUBSCRIPTION) is a publish/subscribe protocol whose subscriber is itself a PostgreSQL database -- it has no native Kafka target. Debezium is a Kafka Connect source connector that consumes the same underlying logical-decoding stream (via the decoderbufs or pgoutput plug-in) and republishes each change as a Kafka record, one topic per table by default. So the real choice for 'streaming changes into Kafka' is not between two competing streaming mechanisms; it is between writing and operating your own consumer of PostgreSQL's logical decoding stream, or adopting Debezium as a maintained, off-the-shelf Kafka Connect consumer of that same stream. Native logical replication alone does not reach Kafka. [8] [2] [1]

### Schema and DDL handling
Neither option replicates DDL. PostgreSQL's own restrictions page states that schema and DDL commands are not replicated by logical replication, and separately that sequence data and large objects are excluded too. Debezium's PostgreSQL connector documentation independently confirms it cannot report DDL change events, for the identical reason: the logical decoding layer beneath it carries no DDL. Any 'add a column and the pipeline breaks' story you may have heard about either approach traces back to this same root cause, not to a design choice either project made. Third-party extensions such as pglogical exist specifically to bolt DDL replication onto native logical replication for Postgres-to-Postgres topologies, which is further evidence the gap is a known, not a hypothetical, pain point. [7] [1] [9]

### Operational risk: replication slots and WAL retention
Both a native subscription and a Debezium connector work by creating and holding a PostgreSQL replication slot. PostgreSQL will not remove any WAL segment the slot might still need; by default (max_slot_wal_keep_size = -1) that retention is unbounded. If the consumer -- a subscriber or a Debezium connector -- stops permanently without the slot being dropped, WAL accumulates on the primary's disk indefinitely. A first-hand incident report describes exactly this failure mode taking a primary down over a quiet weekend after a standby was decommissioned without dropping its slot. This is an operational responsibility that exists identically for either technology choice: whichever one you pick, you need alerting on replication slot lag / restart_lsn and a runbook for dropping a dead slot before it eats the disk. [5] [6]

### Delivery semantics, scaling, and message format
Confluent's documentation for the Debezium PostgreSQL source connector states it is at-least-once (a restart or network fault can produce duplicate Kafka records, so downstream consumers must de-duplicate) and that the connector runs as a single Kafka Connect task -- scale-out means running more connectors (e.g. one per database or table set), not more tasks per connector. On the message-format side, because Debezium's output is Kafka messages, it can serialize records as Avro and track schema versions in a schema registry (Apicurio or Confluent Schema Registry) so consumers can handle a table's schema changing over time; native logical replication has no analogous concept because it never produces an externally-consumed, versioned message schema at all. Separately, if the orders database ends up on a managed PostgreSQL host, verify up front that the platform allows installing a logical decoding plug-in -- Confluent's docs name Heroku Postgres as one host where Debezium cannot be used for exactly that reason. [3] [4]

## 6) Consensus vs Debate
### Consensus
- DDL/schema changes are not carried by either option, because both sit on the same PostgreSQL logical-decoding mechanism. [7] [1]
- Both approaches create a PostgreSQL replication slot and inherit its unbounded-WAL-retention risk if the consumer stops. [5] [6]

### Debate / Contradictory Evidence
- Native logical replication is sometimes framed as the 'simpler' option, but for this specific goal (landing changes in Kafka) it is not a complete alternative on its own: it cannot target Kafka without an additional custom consumer, whereas Debezium is a ready-made Kafka Connect consumer of the same underlying stream. A third-party CDC vendor's public comparison labels native logical replication as the lowest-complexity option and Debezium+Kafka Connect as the higher-complexity, higher-flexibility option -- which is directionally consistent with the projects' own docs, but the source sells a third competing CDC product, so its complexity scoring for the other two should be read as illustrative, not as an independent benchmark. [8] [10]
