`mysql_mode_create_table_syntax.md` / `oracle_mode_create_table_syntax.md` are **faithful mirrors** of the OceanBase V4.5.0 official CREATE TABLE documentation, with no subjective rewriting. But the official BNF itself has a number of gaps — copying it verbatim will not produce valid DDL. This file corrects them item by item, and **takes priority over the BNF mirror**.

## 1. LIST partition enumeration syntax (missing from the official BNF)

The official MySQL-mode `partition_option` production for LIST is:

```text
| PARTITION BY LIST {(expression) | COLUMNS (column_name_list)}
  [subpartition_option] PARTITIONS partition_count
```

Problem: LIST partitioning requires **enumerating values partition by partition**, which `PARTITIONS n` cannot express; and the official documentation never defines `list_partition_list` anywhere. `SUBPARTITION BY LIST(expression)` is likewise missing subpartition enumeration.

The syntax that actually works:

```sql
-- MySQL mode: VALUES IN (...)
CREATE TABLE t_region (
  region_code VARCHAR(8) NOT NULL,
  id BIGINT NOT NULL,
  PRIMARY KEY (region_code, id)
)
PARTITION BY LIST COLUMNS(region_code) (
  PARTITION p_cn VALUES IN ('01','03'),
  PARTITION p_hk VALUES IN ('02'),
  PARTITION p_def VALUES IN (DEFAULT)
);

-- Oracle mode: VALUES (...), note there is no IN
CREATE TABLE T_LOG (
  LOG_VALUE VARCHAR2(8),
  ID NUMBER
)
PARTITION BY LIST (LOG_VALUE)
(
  PARTITION P01 VALUES ('A'),
  PARTITION P02 VALUES ('B'),
  PARTITION P03 VALUES (DEFAULT)
);
```

Key points:

- **MySQL mode uses `VALUES IN (...)`, Oracle mode uses `VALUES (...)`** — the two are not interchangeable.
- Both modes support a fallback `DEFAULT` partition. A LIST partition should include a fallback partition by default; otherwise inserting a value that was not enumerated will fail.

## 2. `AUTO_INCREMENT_MODE` (not in the official BNF, and **MySQL mode only**)

### 2.0 ⚠ Check the compatibility-mode gate first

**The entire `AUTO_INCREMENT` family is MySQL-mode only.** Oracle mode's `table_option` production has none of
`AUTO_INCREMENT`, `AUTO_INCREMENT_MODE`, or `auto_increment_cache_size` (verified line by line against
`oracle_mode_create_table_syntax.md`); Oracle mode uses **the IDENTITY column property** or **sequences** instead:

```sql
-- MySQL mode
CREATE TABLE t (id BIGINT AUTO_INCREMENT PRIMARY KEY, ...)
  AUTO_INCREMENT_MODE = 'NOORDER';

-- Oracle mode (no AUTO_INCREMENT; writing it is a syntax error)
CREATE TABLE T (ID NUMBER GENERATED BY DEFAULT AS IDENTITY, ...);
-- or use a sequence for cross-table numbering
CREATE SEQUENCE SEQ_T START WITH 1 INCREMENT BY 1 NOCYCLE CACHE 100000;
```

The remainder of this section applies **only to MySQL mode**. See `capability-matrix.md` §4 for the complete comparison between both modes.

### 2.1 This option is not in the BNF

The V4.5.0 CREATE TABLE `table_option` list has only `AUTO_INCREMENT [=] INT_VALUE` and
`auto_increment_cache_size` — it **does not have** `AUTO_INCREMENT_MODE`. But both the official auto-increment
column documentation and "Auto-Increment Columns and Sequences Best Practices" list it as a table option usable
at table-creation time.

- `ORDER`: globally ordered numbering, requires cross-node coordination, expensive under high concurrency.
- `NOORDER`: distributed cache-based numbering — each OBServer independently claims a range; **guarantees global uniqueness only, not global monotonic increase** (per-partition increment can still be guaranteed within a partitioned table).
- When not explicitly specified, the tenant parameter `DEFAULT_AUTO_INCREMENT_MODE` applies (default `order` from V4.0+).

### 2.2 Usage criteria

There are two criteria, not one:

1. **Whether the business requires strict monotonic increase.** If not required → NOORDER can be used.
2. **Whether the deployment is multi-node/multi-partition.** The official docs state: in a single-node scenario, ORDER
   and NOORDER show no clear performance difference; NOORDER only shows a clear advantage under high concurrency
   across multiple nodes. There is one more scenario suited to NOORDER: ordered insertion is required, but
   **all Leaders are concentrated on the same OBServer node**.

False criteria to avoid introducing:

- Do not treat "must be a partitioned table" as a precondition — NOORDER's benefit comes from each node independently claiming numbers.
- Do not set a TPS threshold (e.g., "TPS > 100") — there is no basis for it.

### 2.3 Side effects and tuning knobs that must be stated together

- Side effect: **skipped numbers / non-monotonic values** — primary/standby switchover, major compaction, node failure, and restarts can all cause a numbering-segment jump.
- **The magnitude of a skip is determined by `AUTO_INCREMENT_CACHE_SIZE`** (default **1000000**).
  This is the real reason to "use BIGINT"; if the business cannot tolerate skipped numbers, reduce the cache (e.g., 10000),
  at a write-performance cost. This option supports table-level configuration.
- **The MySQL-mode option accepts an integer only.** The V4.5.0 `table_option` production is
  `auto_increment_cache_size [=] INT_VALUE`; `NOCACHE` is an Oracle-mode `CREATE SEQUENCE` clause and is a syntax error here (see §2.3.1).
  **Whether the smallest accepted value disables caching entirely is `unverified`** — the official parameter page documents a
  positive-integer range, and the skill has no confirmed value at which caching becomes a no-op. Confirm on the target
  instance (`tests/integration/mysql_probe.sql`) before promising a business "no gaps"; until then, state only that a
  smaller cache means smaller gaps.
- The corresponding fact on the sequence side: sequences default to `NOORDER` (Oracle-compatible), and the default `CACHE` is only 20 (rather small — specify it manually);
  from V4.2.3, `ORDER + CACHE` is supported, which can satisfy both order preservation and no skipped numbers.

Since `AUTO_INCREMENT_MODE` is not in the mirrored BNF, when generating DDL that includes it, the warnings must note
that "confirmation via testing on the target version is required."

### 2.3.1 `NOCACHE` belongs to Oracle sequences, not to MySQL auto-increment

The two modes reach "fewer gaps" through different syntax, and swapping them produces DDL the server rejects.
This is the exact shape of mistake the `AUTO_INCREMENT`-in-Oracle-mode gate exists to stop, only in the opposite direction —
so it gets its own row here rather than being left implicit.

| Goal | MySQL mode | Oracle mode |
|---|---|---|
| Reduce the gap magnitude | `AUTO_INCREMENT_CACHE_SIZE = 10000` (**integer table option**) | `CREATE SEQUENCE ... CACHE 100` |
| Eliminate caching entirely | **No keyword exists.** Lower the integer; the value at which caching becomes a no-op is `unverified` | `CREATE SEQUENCE ... NOCACHE` (**valid**, costs throughput) |
| Keep order *and* avoid gaps | `AUTO_INCREMENT_MODE = 'ORDER'` (the default) | `ORDER + CACHE`, from V4.2.3 |

```sql
-- Correct: MySQL mode shrinks the integer
CREATE TABLE t (id BIGINT AUTO_INCREMENT PRIMARY KEY, ...)
  AUTO_INCREMENT_MODE = 'NOORDER', AUTO_INCREMENT_CACHE_SIZE = 10000;

-- Wrong: NOCACHE is not a MySQL-mode table option — this is a syntax error
CREATE TABLE t (id BIGINT AUTO_INCREMENT PRIMARY KEY, ...) NOCACHE;

-- Correct: NOCACHE is a sequence clause, so it is Oracle mode only
CREATE SEQUENCE SEQ_T START WITH 1 INCREMENT BY 1 NOCYCLE NOCACHE;
```

## 3. Correct attribution of the deprecation note

The mirror file once placed "deprecated starting from V4.4.1, replaced by SEMISTRUCT_PROPERTIES" right after `DYNAMIC_PARTITION_POLICY`, which is easily misread as meaning the dynamic partition policy has been deprecated.

In the original official text, this note actually belongs to **`SEMISTRUCT_ENCODING_TYPE`**:

```text
| DYNAMIC_PARTITION_POLICY [=] (dynamic_partition_policy_list)
| SEMISTRUCT_ENCODING_TYPE [=] 'encoding' # Deprecated starting from V4.4.1; use SEMISTRUCT_PROPERTIES instead.
| MICRO_BLOCK_FORMAT_VERSION [=] {1|2}
```

`SEMISTRUCT_*` belongs to **semi-structured (JSON) column encoding** and has nothing to do with partition lifecycle. The mirror file has restored this line to match the original text.

**`DYNAMIC_PARTITION_POLICY` is not deprecated and can be used normally.**

The replacement option `SEMISTRUCT_PROPERTIES = (ENCODING_TYPE = ENCODING, FREQ_THRESHOLD = 90)` exists in the official parameter description (from V4.4.1), but does not appear in the V4.5.0 `table_option` production list — this is an inconsistency in the official documentation; test it before use.

## 4. Dangling productions (present as-is in the official documentation)

In the MySQL-mode BNF, `timeline_strategy_list` / `retention_time_unit` are defined but **no production references them anywhere**. This is a leftover in the official documentation, not an omission in the mirror. The agent should not attempt to use these two productions unless a higher-level construct referencing them is found in the target version's documentation.

## 5. Places where the official documents contradict each other (**do not take sides — route by scenario**)

The first four sections deal with "what the official docs left unsaid." This section deals with a different problem:
**two official documents say opposite things**. Arbitrarily picking one side and hard-coding it as a rule would produce
wrong advice in the other kind of scenario. The correct approach is to record the conflict explicitly and state
"which side to follow under which scenario."

### 5.1 "Every table must have a primary key" vs. "a primary-key-less columnstore table is recommended for ETL scenarios"

| Source | Statement |
|---|---|
| "Database Development Best Practices" | "Specify a primary key: **Every table must have a primary key**," and recommends using business columns or a composite primary key rather than an auto-increment column |
| "Table Design and Index Optimization Best Practices" | For the "massive-data ETL analysis" scenario, the recommended approach is precisely a **Columnstore table without a primary key** + time-range partitioning, with the benefit of "improving bulk import performance and lowering management overhead" |

Routing rule:

- **TP tables / tables that need primary-key lookup or incremental sync (OMS/CDC)** → follow the former — require a primary key.
- **Append-only ETL / tracking / log-analytics tables that only do bulk import and analytical scans** → follow the latter — a
  primary-key-less columnstore table is legitimate; the design must not be rejected merely for "having no primary key"
  (this is exactly why the `no_pk_no_uk` branch exists in this Skill's L0 three-branch rule — see `indexes.md` §1).
- A primary-key-less table must still be given the risk notice from `indexes.md` §1.2 (cannot be looked up by primary key,
  OMS/CDC may not be able to integrate, automatic `SIZE` partitioning is unavailable).

Note: OceanBase tables are index-organized by default — **when no primary key is specified, the system generates a hidden primary key** —
so "a primary-key-less table" means "no user-defined primary key," not "genuinely has no ordering key at the storage level."

### 5.2 Auto-increment column type: "must be BIGINT, INT prohibited" vs. "INT is acceptable under specific conditions"

| Source | Statement |
|---|---|
| "Database Development Best Practices" | "You **must** use the BIGINT data type for auto-increment columns. It is **prohibited** to use INT" |
| "Auto-Increment Columns and Sequences Best Practices" | Gives four conditions under which INT is acceptable: data volume far below the INT ceiling; migrating from MySQL where the application must use INT; single-node deployment with rare switchovers; and sufficient monitoring/ops capability (INT→BIGINT conversion supported from V4.2.2) |

Routing rule: **default to BIGINT** (this is this Skill's L1 recommendation). Only allow INT when the user explicitly
states one of the four conditions above (especially "migrating from MySQL, application strongly depends on INT"), and
it must come with the warning: under NOORDER mode, the skip magnitude is affected by `AUTO_INCREMENT_CACHE_SIZE`
(default 1000000), so INT will run out faster than expected → primary key conflict error.

### 5.3 Whether the Oracle-mode primary key must include the partition key

See `capability-matrix.md` §5-5: "Database Development Best Practices," in its Oracle migration section, states
"for a partitioned table or an Oracle heap table, the primary key need not include the partition key," which runs
opposite to the MySQL-mode subset rule. The evidence is insufficient to conclude → **keep as `unverified`**,
Oracle-mode design still follows the stricter MySQL three-branch rule.

## 7. Places where the official partition-lifecycle pages are internally inconsistent

Recorded so the next reader does not have to re-derive them, and because each one is a reason a claim must be
**measured** rather than read off the page.

### 7.1 The drop-partition page's exclusion list says "Truncate"

The Oracle-mode *删除分区* page describes the `UPDATE GLOBAL INDEXES` lazy-maintenance optimisation and then lists
the cases that cannot trigger it — but the first bullet reads *"此时对二级分区执行 **Truncate** 操作"*, on a page
whose entire subject is `DROP`. It looks copied from the *Truncate 分区* page without adaptation.

Two readings: (a) a copy-paste slip, so the exclusion applies to `DROP` as well; (b) read literally, the drop page
never states an exclusion for `DROP` at all. **Do not pick a side in a design.** For a LIST/RANGE first level both
readings give the same answer (not excluded either way); for a HASH first level the readings diverge, so any design
that would rely on reading (b) must prove it by measurement on the target version.

### 7.2 The hidden config appears on only one mode's page

`_ob_enable_truncate_partition_preserve_global_index` (tenant-level; documented as **True** by default on newly
created tenants and **False** on upgraded ones, controlling whether partition DDL leaves global indexes valid)
is documented **only on the MySQL-mode drop-partition page**. The Oracle-mode page does not mention it, and neither
page states how it composes with the Oracle-mode exclusion list. Since an upgraded tenant defaults to the unsafe
value, a design must not assume the safe one → always read the parameter and measure.

### 7.3 `WITH COLUMN GROUP` on a plain `CREATE TABLE`

The Oracle-mode V4.5.0 BNF places `table_column_group_option` only in the `CREATE TABLE … AS SELECT` production,
which reads as if a plain `CREATE TABLE` cannot carry it. The official *创建表* page contradicts this with a working
plain example (`CREATE TABLE tbl1_cg (col1 NUMBER PRIMARY KEY, col2 VARCHAR2(50)) WITH COLUMN GROUP(all columns);`),
so **the BNF omission is the error and the clause is usable**. Still unverified: the same clause *after a partition
clause* — documented clause order says `table option → partition option → column group`, but no official example
shows the combination. `storage-format.md` §1.2 gives the `ALTER` route that avoids depending on it.

## 6. Usage rules

1. When generating DDL, use the mirrored BNF as the syntax baseline;
2. When any item in this file is matched, this file takes precedence;
3. Syntax in this file marked "requires testing" must be surfaced in the output's `warnings` and `checks.capability_matrix`;
4. When any conflict item in §5 is matched, the output must state "which side's criteria were adopted, and on which scenario rule" —
   a bare conclusion is not sufficient;
5. When the target version is not V4.5.0, check `capability-matrix.md` first, then go back to the official documentation to confirm whether this file still applies.
