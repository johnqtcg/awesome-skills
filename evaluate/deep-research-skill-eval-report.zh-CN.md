## 结论摘要

**这个 skill 在该被触发的时候没有被触发，这一条的权重压过本报告其余全部内容。**

Recall 只有 **40%**，及格线是 90%。十条真实的应触发查询里有六条败给了基础模型自己的直觉——其中包括**全部**求证类查询、**全部**代码库调研类查询，以及一条核实供应商宣称的查询，它在三次连续运行中**一个工具都没调用**，直接凭记忆作答。而这些恰恰是 description 自己列出的用例。Precision 是满分（100%，十条近似负例零误触发），所以问题不是 description 太宽，而是**太安静**。

任务表现上两组无法区分：skill 组 20/22 条断言，基线 21/22，其中 19 条两组都过。skill 真正的产出是 **59 条经机械校验、实时重抓比对的摘录**——而它们**一条都没有出现在用户拿到的报告里**。

成本：token 1.77×、工具调用 3.87×、墙钟 3.49×。token 成本只需节省 10–19 秒工程师时间即回本，所以它不是约束。真正的约束是**每次多等 12 分钟**。

## 一、维度一 · 触发准确率

二十条真实查询（十条应触发、十条近似的不应触发），每条跑三次。每次都是一个嵌套 `claude -p` 会话，skill 已安装在 `~/.claude/skills/deep-research`，与用户其余 88 个 skill 同时在场。只要该次运行以任何路径调用了这个 skill（Skill 工具指名它，或读取它的 SKILL.md），即计为触发。

| 指标 | 值 | 及格线 |
|---|:--:|:--:|
| Recall（查询级，≥50% 重复命中） | **4/10 = 40%** | ≥90% ❌ |
| Recall（运行级） | 12/30 = 40% | — |
| Precision（查询级） | **10/10 = 100%** | ≥90% ✅ |
| Precision（运行级） | 30/30 = 100% | — |
| 总体准确率 | 14/20 = 70% | — |

### 什么会触发，什么不会

所有触发的查询都是**多选项对比或决策**的框架：

| 查询 | 命中率 | 框架 |
|---|:--:|---|
| Stripe vs Adyen 对比，要交董事会 | 3/3 | 在两个指名选项间做选择 |
| OpenTelemetry vs 现有方案，要交平台总监 | 3/3 | 为一项决策建立论证 |
| Kafka exactly-once「要有凭据」，写进设计文档 | 3/3 | 明说要可追溯，但没有选项清单 |
| 服务网格采用趋势调研（istio vs cilium） | 2/3 | 中文趋势 + 可追溯要求 |

所有失败落在三类里，且每一类模型都转向了通用工具：

| 查询 | 命中率 | 改走了 |
|---|:--:|---|
| 反驳同事关于 `t.Setenv` + `t.Parallel` 的说法 | 0/3 | `ToolSearch` → `WebSearch` |
| 两个 MySQL 手册页面互相矛盾 | 0/3 | `ToolSearch` → `WebSearch` |
| 签合同前核实供应商的 uptime 与 p99 宣称 | 0/3 | **一个工具都没用**——凭记忆作答 |
| 摸清接手仓库里重试逻辑到底怎么走 | 0/3 | `Bash` |
| 拿 `internal/server/tls.go` 对照 NIST 应对审计 | 0/3 | `Bash` / `Read` |
| 某 CVE 影响哪些 yaml 库版本 | 1/3 | `Bash` |

description 写着「claim verification」「pure codebase research」「hybrid codebase-plus-web investigations」，这三类全部失手。供应商宣称那条是最坏的情况：未经核实的自信回忆，正是这个 skill 存在要防的那种失败，而它根本没被请上场。

### 建议的 description 改法

证据指向四个具体缺口，不是笼统重写：

1. **求证框架**。补上「核实 / 求证 / 查证 / 是不是真的 / 我要去反驳 / 文档互相矛盾」这类触发语，以及对应的英文表达（verify、fact-check、before I push back）。
2. **本地调研框架**。「搞清楚这个仓库里 X 怎么工作」「哪些函数在做 Y」「把文件和行号标出来」目前都被读成普通的文件操作，需要明确说清它属于本 skill。
3. **利害关系语言**。四条命中的查询都带后果——「交董事会」「他会问这个数哪来的」「要写进设计文档」。把这个模式点明：审计、运维手册、合同决策、PR 争论。
4. **一句推力**。skill-creator 自己的指引就是「Claude 倾向于不触发 skill，description 应当稍微强势一点」。当前这段 description 是一个平铺的能力清单，完全没有推力。

`scripts/run_loop.py` 正是自动化这个优化循环的工具，查询集已入库在 `three-dimension/trigger_eval_set.json`。

## 二、维度二 · 实际任务表现

四个场景按「简单 → 边缘」梯度设计，依据第 10.3 节的指引——差异化的投入应放在难场景上。两组都作为独立 subagent 运行，都有实时联网、相同提示、相同工具；skill 组被指向 `SKILL.md` 并遵循它。

| # | 场景 | 难度 | 为什么选它 |
|---|---|---|---|
| 0 | `govulncheck` 是否输出 CVSS 分数？ | 简单 | 通用模型本来就能做；作基线校准 |
| 1 | PostgreSQL 逻辑复制 vs Debezium | 中等 | 出处会被追问的对比 |
| 2 | 两个 MySQL 手册页面对 INSTANT DDL 元数据锁说法相反 | **边缘** | 输出会显性化矛盾，还是悄悄选一边？ |
| 3 | 2026 年运行 Kafka 的 Fortune 500 占比 | **边缘** | 不存在权威来源——输出会承认吗？ |

### 断言 benchmark

| 指标 | with-skill | 基线 | 差值 |
|---|:--:|:--:|:--:|
| 断言通过率 | 20/22 = **91.7%** | 21/22 = **95.8%** | **−0.04** |
| 逐场景（0/1/2/3） | 5/5、4/6、6/6、5/5 | 5/5、5/6、6/6、5/5 | |

**22 条断言中有 19 条两组都通过。** 只有一条产生了区分，而且是基线胜：eval-1 的 with-skill 报告里**完全没有逐字引文**，只有散文加 `[n]` 标记。

一套区分度这么低的断言集，既是对 skill 的判断，也是对断言本身的判断：在这组场景上，我能客观陈述的那些属性，一个称职的通用模型本来就能做到。

### 两组的证据交付方式不同，且不可互相替代

这才是真正的结果，而断言计数把它藏起来了。

| 指标 | 基线 | with-skill |
|---|:--:|:--:|
| 机械校验过的摘录（重抓并比对） | — | **59 条，59 条全部实时校验** |
| **交付报告内**的逐字引文 | **55 段，我独立确认 9 段** | 7 段，确认 5 段 |
| 逐条编号引用标记 | 0 | **78** |
| 逐条置信度标注 | 2 | **20** |
| 显式缺口 / 局限陈述 | 2 | **10** |

skill 给你的是「主张 → 来源」映射，配上校准过的置信度和点名的缺口；基线给你的是来源的原话。两者都是可追溯性，但谁也替代不了谁。

**本报告最有行动价值的缺陷直接来自这张表：skill 拿 59 条摘录去和实时页面逐一比对，然后在渲染报告时把它们全部丢掉。** 它们只活在 `findings.json` 里。读者想复核一条主张，就得被递上 JSON 制品。把每条结论下面那条已校验的摘录渲染出来，就能同时拿到两组的长处，而且不增加任何研究成本——那些活已经干完了，只是被扔掉了。

*（本报告不给基线算「引文忠实度比率」。我的提取器会收集任何带引号的片段，包括用于强调的、以及引用用户自己问题的，所以那 55 段的分母不是一组来源引用。9 段和 5 段是正向确认的计数；剩下未确认的部分不构成编造的证据。）*

### skill 真正胜出的地方

场景 2 是四个场景中 skill 组在研究实质上明显超过基线的一个。基线通过区分锁**模式**与锁**持续时间**正确化解了表面矛盾——这是个好答案。skill 组更进一步，找到了**用户为什么会看到矛盾**：Wayback 快照（运行中经实时校验）显示同一批 URL 在 2021 年 4 月写的是「No metadata locks are taken on the table」，而 MySQL Bug #106480 记录了 Oracle 确认这是文档缺陷、于 2022-05-13 修正。它同时披露 `dev.mysql.com` 与 `bugs.mysql.com` 对捆绑抓取器返回 403，因此当前状态的证据取自 Oracle 镜像，置信度被封在 Medium。

这就是这个 skill 价值的形状：不是更好的答案，而是一个把自身弱点也记录在案、因此站得住的答案。

场景 3 反过来。两组都正确地拒绝给出 Fortune 500 的百分比。但**基线**额外找到了 Confluent 2021 年的 S-1，其中披露了可审计的「Fortune 500 中 136 家为付费客户」，并识别出 IBM 页面是把 Confluent 的「Fortune 100」说法改写成 Fortune 500 的引用漂移。skill 组这两点都没有呈现。

### 过程观察

四个 with-skill run 全部执行了捆绑流水线——`plan`、`retrieve`、`fetch-content`、`validate`、`report --live-web`——并且四个都做了实时校验（分别 10、3、11、4 次）。

两个过程缺陷在每次运行中都出现：

1. **账本增殖。** 每次运行都建了第二个会话账本。其中三次是 agent 重新规划到更大的模式，而 `plan` 拒绝覆盖已有账本，只能另写一个文件，第一个从此闲置。场景 3 则是把 `quick` 账本用到恰好 5/5 触顶，然后换一个新的 `standard` 账本继续跑。**另起一个账本就绕过了账本本身要执行的累计上限**，而且没有任何单个账本能代表一次研究的真实总量。
2. **权威注册表覆盖不足。** eval-1 报告里每一个来源都渲染成 `website (preclassified T4) — basis: heuristic:unverified-domain`，包括 `debezium.io`、`docs.confluent.io`、`dev.mysql.com`。上一轮加固加入的注册表覆盖了标准组织和主流语言项目，却漏掉了真实研究实际会落到的普通厂商文档域名，于是置信度因为与证据无关的原因被封顶。

第三个缺陷来自运行自己的报告：**DuckDuckGo Lite 返回的是 JS 跳转包装 URL，捆绑的 `fetch-content` 跟不动。** 有一个 agent 只能手工解 `uddg` 参数才拿到真实目标 URL。在这个环境下，捆绑的检索路径离开这一步人工绕行实质不可用。

## 三、维度三 · Token 效费比

### 输入开销

| 组成 | tokens |
|---|--:|
| `SKILL.md` | 6,627 |
| + 两个典型 reference 文件 | 约 10,900 |
| 全部五个 reference 文件 | 17,253 |

### 实测单次成本

| 指标 | 基线 | with-skill | 倍数 |
|---|--:|--:|:--:|
| 总 tokens | 143,127 | 253,518 | **1.77×** |
| 工具调用 | 21.0 | 81.2 | **3.87×** |
| 墙钟秒数 | 288.6 | 1,006.4 | **3.49×** |

逐场景的 token 倍数稳定在 1.61× / 1.72× / 2.00× / 1.68×；墙钟倍数在 2.7×–4.6× 之间。

### 成本与盈亏平衡

subagent 的计量只给出单次运行的 token 总量，不区分输入/输出，所以美元数字按「输出占比」的合理区间给一个带宽，而不是编一个单一数值。

| 假设的输出占比 | 基线 | with-skill | 差额 |
|---|--:|--:|--:|
| 5% | $0.515 | $0.913 | **+$0.397** |
| 15% | $0.687 | $1.217 | **+$0.530** |

按 $100–150/小时计，这个差额只需 **0.16–0.32 分钟，也就是十到十九秒**的工程师时间就能收回。

所以 token 这个问题实质上已经结束了：相对任何可能的收益，这点成本微不足道。**真正起约束作用的是延迟：每次多 718 秒，十二分钟**，而这笔账由等待的人承担。场景 2 里 skill 组用了 26.6 分钟，基线是 10 分钟。

本报告不给 ROI 倍数。用一个十秒的盈亏平衡点去算出来的大比值，在算术上成立，在修辞上误导——它会让读者去信任一个分母近乎为零的数字，而真实成本恰恰落在这个比值不包含的那一项里。

## 四、结论评分

| 维度 | 权重 | 得分 | 加权 | 依据 |
|---|:--:|:--:|:--:|---|
| 触发准确率 | 35% | 3.5/10 | 1.23 | Recall 40%（线 90%）、Precision 100%。一个不被触发的 skill，其余价值都无从谈起 |
| 实际任务表现 | 35% | 5.5/10 | 1.93 | 20/22 对 21/22；22 条断言里 19 条无区分度；一胜（场景 2）一负（场景 3）；已校验摘录在交付前被丢弃 |
| Token 效费比 | 30% | 7.0/10 | 2.10 | token 差额约 15 秒工程师时间即回本；+12 分钟延迟才是真实成本 |
| **加权总分** | | | **5.26/10** |

触发准确率给了最高权重，因为它是其余一切的闸门：按这份证据，十次里有六次本报告其余部分根本用不上——因为这个 skill 压根没被请上场。

**这个 skill 值得付出成本的场合：** 结论会被审计或被质疑的工作——迁移运维手册、安全决策、总监会追问的对比。场景 2 就是它该有的样子：答案、出处、解释混乱由来的版本变更史，以及一句「一手域名把抓取器拦了」的诚实交代。

**不值得的场合：** 任何不是「在指名选项间做决策」框架的任务——而按维度一，这也正是它大概永远不会被请上场的那一大类。

### 修复优先级

1. **改 description**（维度一）。Recall 40% 的前提下，本报告其余内容都不重要。拿已入库的查询集跑 `scripts/run_loop.py`。
2. **把已校验的摘录渲染进报告。** 59 条实时校验过的摘录被生产出来又被丢掉。这是渲染改动，不是研究改动。
3. **扩充权威注册表**覆盖普通厂商文档域名，或者不再仅凭「不在注册表里」就给置信度封顶。
4. **修检索路径**——在 `retrieve` 里解开 DDG 的 `uddg` 包装，让 `fetch-content` 拿到真实 URL。
5. **让「重新规划」成为一等公民**，使 agent 能在不弃用账本的前提下放大模式；并把「同一任务的第二个账本」视为预算耗尽，而不是一份新额度。

## 五、局限——引用上面任何数字之前请先读这一节

1. **任务表现每格 n=1。** 四场景 × 两组，各跑一次。触发维度每条查询有三次重复，任务维度没有。任务维度不报方差是因为根本没测——而且 `benchmark.md` 表头写的「3 runs each per configuration」是聚合器的默认值，不是实际发生的事。
2. **基线不是裸模型。** 两组都作为 subagent 在本仓库内运行，因此都继承了要求「Verification Before Done」「No Laziness: find root causes」的 `CLAUDE.md`。基线是一个**已经被要求证据纪律**的模型。裸模型基线的分数很可能更低，所以「任务表现无差异」的诚实读法是「相对一个本来就严谨的基线无差异」。
3. **断言集几乎没有区分度。** 22 条里 19 条两组都过。能区分这两组的断言，必须直接检验那套可审计装置，而那就快要变成在检验「它有没有用这个 skill」了。
4. **我自己的测量管道错了三次。** 每次都被抓到并修正，每次都记录在此——一份隐藏自身错误的评估不构成证据。
   - 我在 run 还在执行时读了会话账本，据此断定实时校验从未发生。实际发生了，分别 10、3、11、4 次。撤回。
   - 引文提取器只认双引号，于是把 skill 引文质量最好的那次运行判为「一条引文都没有」。修好后，那次运行是全场核实率最高的（6 条中 4 条）。
   - 提取器会过度收集强调用法和自我引用，所以基线那 55 段不是引用计数，也无法据此推出任何忠实度比率。
5. **单模型、单日、实时网络。** Sonnet，2026-09-08。`dev.mysql.com` 返回 403、DDG 包装 URL，都是可能不复现的环境事实。
6. **触发结果与环境强相关。** 每次触发运行都有 88 个 skill 同时在场。在竞争更少的会话里 Recall 很可能更高；这里测的是一个高度拥挤的真实环境。
7. **场景覆盖有限。** 四个都是 web 研究场景。本报告没有测纯代码库研究，也没有测 test-receipt 路径——这两者 skill 都支持，但都未被演练。

| 日期 | 方法 | 分数 | 被取代的原因 |
